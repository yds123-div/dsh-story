# oh-story 产品平台设计基线

- 状态：首期边界已确认，细节待实现验证
- 日期：2026-09-21
- 主仓库：`D:/Shenlan/dsh-story`
- 来源：`web-oh-story` 前端、`dsh-story` 创作技能与 `deepblue-harness` 集成探索

## 1. 文档目的

本文档记录将 `dsh-story` 发展为短剧创作产品主仓库时已经确认的方向、边界和待决问题。它不是最终 PRD、数据库设计或 API 规格，不应在细节尚未讨论前锁死实现。

核心原则：

> `dsh-story` 定义短剧创作阶段和产物边界；`deepblue-harness` 提供 Agent/LLM/Session/Task 运行能力；产品后端负责项目数据、阶段确认、任务和媒体；产品前端负责查看、审阅和推进这些产物。首期运行在单用户或受信环境中，不实现项目权限、在线编辑和对象存储。

## 2. 已确认的仓库方向

### 2.1 主仓库

`dsh-story` 成为产品主仓库。现有 `web-oh-story/frontend` 迁移到 `dsh-story/apps/web`，不保留原 Git 提交历史。

产品后端新增到 `dsh-story/apps/api`。前后端仍然是两个独立进程，单仓库不改变前后端分离关系。

### 2.2 Harness 关系

不把 `deepblue-harness` 源码复制进 `dsh-story`。`dsh-story` 通过 workspace、固定版本、Git 或本地路径依赖使用 Harness；只有需要联动修改 Harness 本身时，才考虑建立上层总工作区。

现有 `oh-story-skills`、`oh-story-roles`、`oh-story-workspace` 和 `bundle-oh-story` 保持独立边界。产品后端通过稳定入口调用它们，不让产品页面直接依赖其内部实现。

### 2.3 迁移策略

迁移分阶段完成：

1. 在 `dsh-story` 建立产品应用目录和共享包目录；
2. 迁移前端并先确保新位置可启动、构建、路由和 Mock 正常；
3. 新增产品后端骨架；
4. 先打通剧本阶段真实闭环；
5. 再按 `dsh-story` 重构资产、分集、分镜和生产页面；
6. 新仓库稳定后，再决定是否归档 `web-oh-story`。

迁移期间不删除旧仓库。

## 3. `dsh-story` 创作模型是产品主模型

产品不再默认当前前端三步流程正确。前端现有页面只是原型和交互参考，需要根据 `dsh-story` 的阶段契约重构。

`dsh-story` 的阶段 owner 和产物边界优先于当前页面结构。

### 3.1 五类创作产物

| 创作产物 | 主要职责 | 明确不负责 |
|---|---|---|
| 剧本 | 场景、动作、对白、声音事实、画面文字、剧情状态 | 资产图、分镜、媒体生成 |
| 视觉设定 | 角色身份、造型变体、地点、道具、状态、连续性 | 镜头走位、图片/视频提示词 |
| 图片提示词 | 将视觉事实转成可复制的图片生成规格 | 直接调用图片模型 |
| 分镜 | 镜头职责、空间关系、起止状态、冻结关键帧 | 直接生成视频 |
| 视频提示词 | 动作、表演、运镜、声音、时序、可验证终点 | 直接调用视频模型 |

实际媒体生产是独立运行边界：先生成生产预览，用户看到当前任务后明确确认，再调用 adapter。

### 3.2 五类产物的产品映射

产品不要求用户看到五个原始 Markdown 页面，但不能在领域上合并它们。前端可以用总览、Tab、抽屉和折叠区组织展示；后端仍需分别保存和管理五类产物。

```text
产品总览
├── 剧本阶段
│   ├── 剧本分析
│   ├── 剧本正文
│   └── 资产候选
├── 资产阶段
│   ├── 视觉设定
│   ├── 图片提示词
│   └── 图片生产
└── 制作阶段
    ├── 分集规划
    ├── 分集剧本
    ├── 分镜
    ├── 视频提示词
    └── 媒体生产
```

## 4. 剧本模式与小说模式

### 4.1 剧本模式

剧本模式处理已有剧本，主要职责是：

- 必要的格式规范化；
- 保留创作者事实的精编；
- 场景、角色、对白、动作和声音事实识别；
- 制作可行性检查；
- 资产候选提取；
- 输出用户可审阅的只读剧本产物。

剧本模式不强制虚构完整故事开发文档，也不应擅自改变主角、核心冲突、结局或创作意图。

### 4.2 小说模式

小说模式才承担完整改编链路：

```text
小说分析
  → 改编方案
  → 分集候选
  → 短剧剧本
  → 用户审阅
  → 资产候选
```

前端可以保留一次“开始创作”的入口，但不能把小说模式宣传成“一键转视频”。该标语删除；后台仍需保留阶段边界和中间产物。

## 5. 剧本到资产的确认闸门

产品首期主流程暂定为：

```text
创建项目并粘贴/上传剧本
  ↓
剧本生成运行
  ↓
展示只读的剧本分析、正文、场景索引和资产候选
  ↓
用户选择并接受某次剧本运行结果
  ↓
运行资产拆解
  ↓
展示只读的资产候选
  ↓
用户接受资产候选
  ↓
进入视觉设定和后续生产阶段
```

大纲页只展示资产候选，不把候选冒充正式视觉资产。首期不提供在线编辑或 AI 修改剧本；用户发现问题时，可基于原始输入重新运行，产生新的独立只读结果。只有接受剧本后，才能运行资产拆解；只有接受资产候选后，才能进入视觉设定。

## 6. 大纲页的产品方向

大纲页不再以固定的“智能体剧组创作会议”作为主要内容。固定聊天消息不能冒充真实创作产物。

首期改成“剧本创作总览工作台”，采用“总览 + 分阶段 Tab”：

### 6.1 顶部阶段状态

显示当前项目处于：

- 剧本生成中；
- 剧本审阅；
- 等待接受；
- 资产候选待确认；
- 视觉设定处理中；
- 可进入下一阶段。

### 6.2 剧本工作区

展示：

- 标题、类型和主角；
- 故事摘要；
- 本集观看承诺；
- 本集目标、阻力、结果和退出状态；
- 场景导航；
- 规范化剧本正文；
- 对白、动作、声音和画面文字；
- 当前生成运行、运行时间和任务状态；
- 重新运行入口；
- 不提供用户编辑入口。

### 6.3 分析和检查区

展示：

- 故事分析；
- 角色目标、策略、筹码和关系状态；
- 场景功能；
- 制作检查；
- 未决指代；
- 资产候选及其来源证据；
- 进入下一阶段前必须处理的问题。

### 6.4 接受动作

每次生成产生一组独立的只读运行结果。用户可以查看、拒绝，或选择其中一份提升为当前有效剧本。当前推荐一次接受该剧本产物包，包括：

- 规范化剧本；
- 剧本分析；
- 场景索引；
- 资产候选；
- 制作检查结果。

接受剧本会将该次运行结果提升为项目当前有效剧本，并允许运行资产拆解。接受资产候选不等于接受正式视觉资产；正式视觉资产要在资产阶段单独确认。

同一项目重新运行时，不覆盖旧运行结果，不合并不同运行结果。旧结果保留为历史记录，并标记为已拒绝、未选定或已选定等状态。

## 7. 资产模型与资产页方向

资产按照 `dsh-story` 的视觉事实建模，而不是简单的生成卡片。

### 7.1 三层结构

```text
资产身份
  └── 视觉变体
        └── 镜头瞬态
```

- 资产身份：例如“林晚”“木叶长廊”“苦无”；
- 视觉变体：服装、伤势、时段、天气、开合或持有状态的变化；
- 镜头瞬态：姿势、视线、站位和机位，由分镜负责。

视觉设定至少输出：

- 识别锚点；
- 本集造型/状态；
- 不变量；
- 可变化部分；
- 出现位置和来源证据；
- 跨场连续性；
- 未决指代。

### 7.2 资产来源

资产必须支持：

- AI 生成；
- 用户上传；
- 项目内已有资产复用；
- 视觉变体；
- 默认参考图；
- 跨集连续性。

需要区分“图片提示词条目”和“真实参考图”：提示词条目不代表已有图片，真实参考图必须有独立身份和控制范围。

### 7.3 生成策略

第一阶段允许资产逐项生成，不强制实现批量生成。后端数据模型可以预留批次任务，但不把批量 UI 和调度复杂度作为首期阻塞条件。

## 8. 分集、分镜和视频提示词

当前前端把分集、片段、分镜和视频提示词压缩在同一个 Segment 对象中，需要按照 `dsh-story` 重新拆分。

推荐层次：

```text
分集规划
  ↓
分集剧本
  ↓
片段/连续场面
  ↓
分镜 Shot
  ↓
冻结关键帧
  ↓
视频提示词 Motion
  ↓
媒体生产
```

### 8.1 分集

负责本集的进入状态、当集目标、阻力、转折、结果、信息释放和下一集交接。

### 8.2 片段

负责连续场面、场景、出场人物、起止状态、时长和在整集中的位置。

### 8.3 分镜

负责镜头职责、景别、机位、空间、人物位置、视线、动作起点/终点、对白、声音、画面文字和视觉依据。

### 8.4 视频提示词

负责从分镜起点到终点的静态锚点、触发动作、主体表演、次级反应、运镜、声音、节奏和禁止漂移约束。

产品不应把分镜和视频提示词合并。首期视频生产按单个分镜创建任务，便于追踪、失败隔离和局部重试；后续如支持片段或镜头组生产，也不能因此合并领域文档边界。

## 9. 图片、视频和声音生产

生产任务按 modality 分开：

```text
image | video | tts | music
```

第一阶段优先接入：

1. 文本模型；
2. 图片模型；
3. 视频模型。

TTS 和音乐在数据模型中预留，创作阶段先保存对白、表演要求、声音方向和音乐意图；真实音频供应商可以后续接入。

所有媒体生产都遵循：

```text
创作产物
  ↓
生产预览
  ↓
用户看到当前任务并明确确认
  ↓
adapter 执行
  ↓
记录结果和运行信息
```

预览、上游接受或“继续”不能替代本次具体生产确认。

## 10. 项目内创作助手

固定聊天展示后续可以改造成绑定项目和阶段的“项目内创作助手”。首期不把助手作为剧本编辑器，也不允许助手修改或覆盖创作产物。

首期允许：

- 解释当前剧本或资产候选；
- 回答项目内问题；
- 找出角色、场景和资产出现证据；
- 检查是否满足进入下一阶段的条件；
- 在用户明确确认后触发下一阶段任务。

首期不允许：

- 提出或执行剧本修改提案；
- 未经确认覆盖文档；
- 自动修改多个阶段；
- 自动调用付费媒体模型；
- 自动跳过生产确认；
- 自主运行完整项目流水线。

用户发现剧本问题时，首期只能回到原始输入重新运行，产生新的独立只读结果。在线编辑、AI 修改提案、差异审阅和下游影响分析属于后续能力。

助手可以在用户明确表达“接受剧本”“进入资产拆解”等意图后调用产品后端动作，但不能直接绕过后端状态和确认检查。

## 12. 数据真相边界

首期边界：

- 五类创作文档拥有创作事实；
- 产品数据库保存项目、运行记录、任务、用户接受结果、结构化查询投影和文件元数据；
- 原始输入和生成文件先保存到本地运行目录，数据库保存文件引用；
- 前端只通过产品 API 访问数据；
- 首期生成产物只读，不提供前端或 Agent 直接修改；
- 每次生成产生独立运行结果，新的运行不得覆盖旧结果；
- 用户接受某次运行后，该结果成为项目当前有效产物，并允许进入下一阶段；
- 同一任务的重复请求使用幂等语义，避免重复创建运行或重复生成产物。

首期不建立项目所有者、协作者、角色或权限字段，默认运行在单用户或受信环境中。首期也不引入对象存储抽象；后续可以在不改变业务产物模型的前提下替换文件存储实现。

不能出现前端直接修改数据库字段、但对应 `dsh-story` 产物没有变化的双重真相。

## 13. 暂不纳入首期范围

以下内容不阻塞第一条剧本到视觉设定的真实闭环：

- 在线编辑剧本或其他创作产物；
- AI 修改提案、差异审阅和下游影响分析；
- 复杂版本树、分支合并和复杂回滚；
- 项目所有者、协作者、角色和权限控制；
- 多租户隔离；
- 对象存储和可切换文件存储后端；
- 完整批量资产调度；
- 完整 TTS 供应商接入；
- 音乐模型接入；
- 节点画布后端编排；
- 积分和计费；
- 全自动 Agent 流水线；
- 复制完整 `deepblue-harness` 源码；
- 一次性重写所有前端页面。

## 14. 下一轮需要继续讨论的问题

### D1：分集与分镜确认点

需要确定分集规划、分集剧本、分镜、视频提示词之间哪些必须用户确认，哪些可以自动串联生成。

### D2：产品 API 与 Harness 的调用契约

产品 API 已确定为独立进程。下一步需要确定它调用 Harness 的稳定入口、任务回调或轮询方式，以及失败和超时的统一映射。

### D3：后续文件存储替换

首期使用本地文件和数据库元数据。后续如果接入对象存储，需要保持业务产物引用不变，并确定迁移、访问授权和媒体 URL 策略。

### D4：视频生产粒度

首期视频生产按单个分镜创建任务；后续仍需结合目标视频模型确定是否支持片段或镜头组生产。无论选择哪种，`分镜`和`视频提示词`仍保持独立产物。

## 15. 当前建议的首条验证闭环

先不要同时开发所有媒体能力，优先验证：

```text
apps/web
  ↓ 粘贴/上传剧本
apps/api
  ↓ 创建项目和剧本任务
dsh-story 剧本阶段能力
  ↓ 生成结构化剧本产物
apps/api
  ↓ 保存文档和投影
apps/web
  ↓ 展示剧本分析与正文
用户接受剧本
  ↓
apps/api 运行资产拆解
  ↓
前端展示资产候选
```

这条闭环验证成功后，再进入正式视觉设定、图片提示词、图片生产和分镜流程。
